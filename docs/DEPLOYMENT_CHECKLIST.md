# Production deployment checklist

## Before deployment

- [ ] Confirm `.env.local` and all `.env.*` files remain ignored and unstaged.
- [ ] Confirm Vercel contains the required environment variable names: `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SESSION_SECRET`, `ADMIN_USERNAME`, `ADMIN_PASSWORD_SCRYPT`, `LINE_CHANNEL_ACCESS_TOKEN`, `LINE_LOGIN_CHANNEL_ID`, `LIFF_ID`, `ADMIN_LINE_USER_ID`, and `CRON_SECRET`.
- [ ] Verify Production and Preview each have a cryptographically random `SESSION_SECRET` of at least 32 characters and an `ADMIN_PASSWORD_SCRYPT` generated by `node scripts/hash-password.mjs`. Remove `ADMIN_PASSWORD_BASE64`. Rotate `SESSION_SECRET` when rolling out the cookie-based session and have admins sign in again. Keep the patched session code and rotated secret in any replacement deployment.
- [ ] Confirm the latest SQL migrations have been applied to the intended Supabase project.
- [ ] Run `npm run release:gate` and require a zero exit code.
- [ ] Run `npm run audit:security` and resolve every high/critical production dependency finding. Build-only tooling is isolated from user input and reviewed separately before upgrades.
- [ ] Confirm the LIFF endpoint and allowed redirect URLs point to the production domain.
- [ ] Review the staged file list and verify that no environment file, token, exported data, or QA screenshot is included.

## Inventory and employee access rollout

- [ ] Use a staging copy of the Supabase schema and representative historical records to verify the migration order. Apply `supabase/migrations.sql` first if the existing installation has not applied it, then apply `002_inventory_integrity.sql`, `003_issue_reporting.sql`, `004_legacy_issue_reconciliation.sql`, and `005_issue_feedback.sql` in that order.
- [ ] Back up the production database and schedule a maintenance window. Pause inventory writes while applying the migrations and switching to the updated app so older application instances cannot allocate conflicting IDs or bypass inventory transactions.
- [ ] Populate `ppe_employee_access` from the verified employee roster and verified LINE identities before granting access. The roster row needs `line_user_id`, `employee_id`, `employee_name`, `department`, and `active = true`. The department must match the master department name. Employees can see their own verified LINE ID on the access screen. Confirm the mapping through the organization's identity verification process before creating or reactivating the row.
- [ ] Confirm the anon and authenticated database roles cannot read the inventory or employee tables directly. Confirm the `documents` bucket is private, old public URLs fail, and authorized staff receive five-minute signed links. Legacy documents with same-project public URLs reuse their existing objects. Copy externally hosted documents into the private bucket and set their `storage_path` to the verified object path.
- [ ] Review historical approved rows with `approved_items IS NULL`, and review old vouchers still marked `processing`. Partial approvals with a single matching audit record are backfilled. For the remaining records, compare receipts, audit evidence, and physical inventory before filling quantities or changing statuses. The migration only backfills documented quantities and does not change existing balances. Keep unresolved vouchers flagged until evidence is available.
- [ ] Verify a partial approval with a zero-approved line, receipt confirmation, rating the delivered line, and the same figures in the report, CSV, and PDF. Verify cancellation returns the exact approved quantities once for an unreceived voucher and retains the original voucher and movement history.

## Operational reliability rollout

- [ ] After `005_issue_feedback.sql`, apply `006_inventory_categories.sql` and `007_document_lifecycle.sql` before switching to the updated app.
- [ ] Review items with `category_id IS NULL` and old labels that match multiple categories after trimming and case normalization. Use the Admin item form to choose the verified category for active items. Review archived rows separately. The foreign key protects category references on both active and archived items.
- [ ] Upload a private PDF just under 3 MiB and open it through a signed link. Try a file over the limit and confirm rejection. Delete a test document and verify it is removed from Storage. A deferred deletion is hidden from the catalog immediately and retried by the maintenance job.
- [ ] Confirm the CI job **Release checks** passes. Require that job in the protected `main` branch settings before merging deployment changes. CI runs on Node.js 24 with offline Supabase placeholders, Chromium, and the existing release gate.
- [ ] Confirm the scheduled maintenance job has `CRON_SECRET` and an enabled LINE recipient for the `system` topic. Configure alerts on the structured event names in [Production observability](OBSERVABILITY.md) so incidents remain visible when Supabase or LINE is unavailable.

## Deployment

- [ ] Deploy the verified commit only.
- [ ] Confirm `/index.html` and `/api/ppe` respond over HTTPS.
- [ ] Confirm the CSP permits the LINE LIFF SDK and required Supabase connections without browser violations.
- [ ] Confirm `X-Request-Id`, `X-Content-Type-Options`, `Referrer-Policy`, and CSP headers are present.

## Post-deployment smoke test

- [ ] Open through LINE and confirm login/profile loading.
- [ ] Sign in as admin, reload the page to verify session continuity, then sign out and verify admin access is removed. Check that the application session cookie has the `HttpOnly`, `Secure`, and `SameSite=Strict` flags.
- [ ] Check user stock, issue, loan, history, and PPE standards modules.
- [ ] Check admin pending, manage, receive, report, and notification modules.
- [ ] Use a controlled test account to complete one approved issue and receipt-confirmation flow.
- [ ] Confirm the Flex notification contains the correct item image and deep link.
- [ ] Confirm Vercel logs contain `api_request` and `client_telemetry_batch` entries without personal or secret data.
- [ ] Check desktop at 1920 px and mobile at 390 px for overflow and blocked controls.

## Rollback

- [ ] If the inventory migrations have run, pause writes before switching deployments. Use a replacement build compatible with the inventory schema and private storage. Do not resume writes on a build that still allocates IDs with `MAX(id) + 1`.
- [ ] If critical flows fail, immediately promote the previous known-good Vercel deployment.
- [ ] Do not roll back database migrations that contain production data without a reviewed recovery plan.
- [ ] Record the failed deployment ID, request IDs, symptom, and rollback time for follow-up.
